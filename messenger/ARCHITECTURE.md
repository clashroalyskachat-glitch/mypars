# pps — как всё устроено

Коротко: **ванильный фронтенд + Supabase + Google Apps Script + Firebase Hosting**.
Без фреймворка, без собственного сервера. Всё бесплатное.

```
Браузер
  ├─ index.html + app.js + styles.css
  ├─ Supabase JS SDK (REST, Realtime, Presence)
  ├─ Firebase Messaging SDK (push)
  └─ service worker firebase-messaging-sw.js
        │
        ├── Supabase (Postgres + RLS + Realtime)
        │     profiles, chats, chat_members, messages, signals
        │
        ├── Google Apps Script (web app /exec)
        │     вход/регистрация, JWT для Supabase,
        │     удаление сообщений, Google Drive, Telegram-паки,
        │     FCM push, таблицы пользователей/сессий/токенов
        │
        └── Firebase Cloud Messaging
              push о сообщениях и звонках
```

## Фронтенд

- `index.html` — вся разметка: чаты, настройки, QR, сканер, звонок, стикеры.
- `app.js` — один IIFE, без сборки и зависимостей. Прямая работа с DOM.
- `styles.css` — дизайн-система на CSS-переменных, темы, акценты, стекло, адаптив.
- `config.js` — публичные ключи Supabase и Firebase, URL Apps Script.
- `qrcode.js` — генерация QR.
- `jsqr.min.js` — декодер QR, подгружается **только** при сканировании.
- `supabase.js` — Supabase SDK локально.
- `firebase-messaging-sw.js` — service worker для push.

Состояние — один объект `state`. История и настройки — в `localStorage`.
Сообщения отправляются **оптимистично**: сначала появляются в UI, потом уходят в базу.

## Вход и аккаунты

- Аккаунты — старые колледжные, из Google Таблицы (`Пользователи`).
- Пароль: `SHA-256(salt + ':' + password)`, соль на пользователя.
- Сессия: случайный токен в листе `Сессии`, живёт 30 дней.
- Есть лимиты: 8 неверных паролей — блокировка ника, плюс лимиты на регистрацию.
- Клиент хранит `nkse-session` (токен + ник).
- Apps Script подписывает **Supabase JWT** (HS256) секретом `SUPABASE_JWT_SECRET`.
  JWT живёт 12 часов; клиент обновляет его по таймеру, при фокусе и перед отправкой.
- В Supabase JWT: `sub` = старый uid, `role` = `authenticated`, `nick`.

## База и доступ

Таблицы:

| Таблица | Что хранит |
|---|---|
| `profiles` | `id`, `nick`, `last_seen` |
| `chats` | 1:1 и группы (группы пока не используются) |
| `chat_members` | кто в каком чате |
| `messages` | сообщения: `chat_id`, `sender_id`, `body`, `client_id` |
| `signals` | временные WebRTC-сигналы |

- Везде включён **RLS**. Читать чат/сообщения может только участник.
- `create_direct_chat(other_id)` — security definer, создаёт или находит 1:1 чат.
- `client_id` + уникальный индекс защищают от дублей при повторной отправке.
- Удаление «у всех» идёт через Apps Script: он проверяет, что ты участник чата,
  и удаляет строку сервисным JWT. Это обходит RLS, поэтому проверка обязательна.

## Realtime

- `pps-online` — Presence: кто онлайн, кастомный статус, режим «скрыт».
- `user-<uid>` — личные Broadcast-события: сообщения, сигналы звонка, удаления.
- `chat-<chatId>` — Broadcast сообщений в открытом чате.
- Плюс опрос базы как страховка:
  - открытый чат — раз в 1 с;
  - все чаты — раз в 1.5 с;
  - сигналы звонка — раз в 1 с.
- Сообщение сначала летит Broadcast, потом пишется в Postgres.
  Получатель дедуплицирует по `client_id`, сигналы — по `sid`.

## Сообщения

- Текст, эмодзи, стикеры и вложения кодируются маркерами в `body`:
  - `[[img:url|подпись]]`
  - `[[file:url|имя|подпись]]`
  - `[[sticker:url]]`
  - `[[call:audio|статус|секунды]]`
- Поэтому не нужны новые колонки и SQL при добавлении типа сообщения.
- Удаление у себя — локальная метка. Удаление у всех — удаление строки + Broadcast.
- Плашки звонков отправляет только звонящий, второй участник получает готовую.

## Звонки

- Чистый WebRTC P2P: `RTCPeerConnection`, аудио и видео.
- STUN: Google. TURN: бесплатный `openrelay.metered.ca`.
- Сигналинг: Broadcast `user-<uid>` + резервная запись в `signals`.
- Оффер → ответ → ICE-кандидаты. Есть защита от дублей по `sid`.
- Камера в аудиозвонке включается **реагированием**: `addTrack` + новый offer/answer.
- Звук собеседника идёт через отдельный `<audio>`, видео — через `<video muted>`.
  Это лечит баг, когда на некоторых браузерах видео в `display:none` не играло звук.
- Есть: приём/отклонение, таймауты, завершение, «связь потеряна»,
  вибрация, удержание экрана (`wakeLock`), полноэкранный режим, масштаб.
- Статус «в звонке» ставится только после реального `connected`.

## Push

- Firebase Web App + VAPID-ключ.
- Клиент регистрирует FCM-токен и отправляет его в Apps Script.
- Apps Script хранит токены в листе `PushTokens` (несколько устройств на ник).
- Отправка — FCM v1 через service account (RS256 JWT → OAuth → FCM).
- Payload только `data`, уведомление рисует service worker.
- Клик по уведомлению открывает чат; для звонка — с `call=1`.

## Файлы, стикеры, QR

- Файлы: Apps Script принимает base64, кладёт в папку **«PPS Медиа»** на Google Диске,
  открывает доступ по ссылке. Картинки сжимаются до 1600px JPEG, лимит 8 МБ.
- Показ картинок — через Drive `thumbnail`, а не `uc?export=view`
  (второй браузеры блокируют).
- Стикеры: emoji-паки в `localStorage`, паки по URL картинок.
- Telegram-паки: Apps Script `getStickerSet` → `getFile` → Google Диск.
  Берутся только статические `.webp`, до 16 за импорт.
- QR: `qrcode-generator` для показа, `jsQR` для сканирования камерой или фото.

## Дизайн и производительность

- CSS-переменные: тёмная/светлая тема, 4 акцента, стекло, зерно, тёплая палитра меню.
- Анимации только `transform`/`opacity`.
- `contain` на декоративных слоях, ленивый jsQR, ленивый Firebase SDK.
- На слабом устройстве включается `pps-low-power`: отключаются тяжёлые эффекты.
- На телефоне — отдельная раскладка, свайп-навигация, безопасные отступы.
- Service worker для `/messenger/` — network-first, чтобы обновления прилетали сразу.

## Сборка и хостинг

- `npm run build` — esbuild собирает основной сайт и копирует `messenger/`.
- `npm run build:firebase` — раскладывает в `firebase-dist`.
- `firebase deploy --only hosting` — публикует на `nkselove.web.app`.
- Apps Script обновляется через `clasp push` + `clasp deploy`.

## Слабые места

1. **Apps Script — самое слабое звено.** Квоты, задержки, лимит 6 минут,
   Google Таблицы вместо нормальной БД для сессий и токенов.
2. **Пароли** — быстрый SHA-256, а не Argon2id/bcrypt. Нет 2FA и восстановления.
3. **Нет E2EE.** Сообщения лежат в Postgres открытым текстом. RLS защищает доступ,
   но не от самой базы.
4. **TURN бесплатный и нестабильный.** Звонки через мобильный интернет могут рваться.
   Групповых звонков и демонстрации экрана нет.
5. **Push только веб.** На iPhone — только если сайт добавлен на «Домой».
   Полноценный фоновый звонок при закрытом браузере невозможен без нативного приложения.
6. **Файлы на Google Диске** — не CDN, есть квоты и ограничения на шаринг.
7. **Опрос каждую секунду** — просто и надёжно, но плохо масштабируется.
8. **Нет пагинации истории** (последние 200), поиска по сообщениям, галереи,
   групповых чатов, статусов прочтения и «печатает…».
9. **Ванильный JS** — легко и быстро, но чем больше фич, тем сложнее поддерживать.

## Что бы я взял вместо этого, если делать заново

| Сейчас | Альтернатива |
|---|---|
| Apps Script auth + JWT | Supabase Auth (GoTrue) или Clerk |
| Apps Script функции | Supabase Edge Functions / Cloudflare Workers |
| Google Таблицы для сессий | Postgres |
| Google Диск для файлов | Supabase Storage / Cloudflare R2 / S3 |
| P2P WebRTC + openrelay | LiveKit (SFU + TURN + запись + группы) |
| FCM + service worker | FCM + Capacitor/React Native для фоновых звонков |
| Ванильный JS | Svelte / Solid / Preact, если проект растёт |
| Свой протокол сообщений | Matrix (Synapse) или XMPP, если нужна федерация и E2EE |
| SHA-256 пароли | Argon2id |
| Нет E2EE | MLS (openmls) или Signal Protocol |

## Что уже хорошо

- Нет фреймворка и лишнего веса.
- Supabase RLS реально ограничивает доступ.
- Broadcast + резервная запись в БД: сообщения и сигналы не теряются при сбоях.
- Оптимистичный UI и дедупликация.
- Всё работает на бесплатных тарифах.
- Дизайн и анимации не грузят слабые устройства.
