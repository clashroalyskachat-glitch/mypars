# pps — как ускорить до «мгновенно»

## Диагноз

Сейчас каждое действие — это **новый последовательный HTTP-запрос к удалённой базе**.
Ничего не кэшируется локально, поэтому интерфейс всегда ждёт сеть.

Замеры на проде:

| Операция | Время | Из чего состоит |
|---|---|---|
| Отправка (своё сообщение) | 4 мс | оптимистичный рендер |
| Запись в БД | 137 мс | один REST INSERT |
| Доставка получателю | ~240 мс | INSERT + postgres_changes |
| Открытие чата | 350–520 мс | профиль → RPC чата → сообщения |
| Удаление «у всех» | 2600–3500 мс | Apps Script |
| Файл | 5–15 с | base64 → Apps Script → Drive |
| Push | 3 с+ | Apps Script → FCM |

Причина не в Supabase и не в WebRTC. Причина в **структуре**:

1. UI не имеет своего состояния — он всегда спрашивает сервер.
2. Каждое открытие чата — 3 запроса подряд, хотя нужен один.
3. Всё, что не сообщения, идёт через Apps Script (3 секунды на вызов).
4. Файлы идут через Apps Script на Google Drive, а не напрямую в хранилище.

Telegram и Discord работают наоборот: **локальный кэш — источник истины для UI**,
сеть только догоняет. Открытие чата у них — чтение из памяти, 0 мс.

---

## Принцип: local-first

```
Клик по контакту
  ├─ сразу: показать чат из IndexedDB (0 мс)
  ├─ сразу: показать последние сообщения из кэша (0 мс)
  └─ фоном: один запрос «что нового после X» → слить → перерисовать
```

Правило: **пользователь никогда не ждёт сеть, чтобы увидеть то, что уже видел раньше.**
Сеть нужна только для нового.

Это даёт «супер быстро» без смены стека и без денег.

## Слой 1. Прямой проход для известных контактов

Сейчас при каждом открытии:

```js
await profiles.select('id').eq('nick', peer.nick)   // 163 мс — даже если uid уже известен
await rpc('create_direct_chat', { other_id: uid })  // 140 мс — даже если chat_id уже известен
await messages.select('*').eq('chat_id', chatId)    // 215 мс
```

Нужно:

```js
// 1. uid и chatId уже есть в localStorage → пропускаем первые два запроса
const cached = chatCache.get(peer.nick); // { uid, chatId, lastTs }
if (cached) {
    renderFromCache(cached.chatId);   // 0 мс
    fetchNew(cached.chatId, cached.lastTs); // 1 запрос в фоне
    return;
}
```

- `uid` приходит из поиска контактов и сохраняется.
- `chatId` сохраняется после первого открытия.
- Профиль по нику запрашивается **только** если uid неизвестен.
- `create_direct_chat` вызывается **только** если chatId неизвестен.

Эффект: повторное открытие чата — **0 мс до картинки**, ~200 мс до свежих сообщений.

### Вариант без кэша: детерминированный chat_id

Если не хочется зависеть от кэша, id чата можно вычислять из двух uid:

```sql
create or replace function direct_chat_id(a text, b text)
returns uuid language sql immutable as $$
    select uuid_generate_v5(
        '00000000-0000-0000-0000-000000000000'::uuid,
        least(a, b) || ':' || greatest(a, b)
    );
$$;
```

Тогда `chatId` известен всегда, и `create_direct_chat` не нужен в горячем пути.
Строку в `chats` можно создать лениво при первом сообщении (upsert).

Минус: нужно перенести существующие чаты или оставить кэш как переходный слой.
Поэтому проще начать с кэша, а детерминированный id добавить позже.

## Слой 2. Один запрос на открытие

Вместо трёх запросов — одна RPC:

```sql
create or replace function open_chat(
    other_id text,
    before   timestamptz default null,
    page     int default 50
)
returns jsonb
language plpgsql security definer as $$
declare
    cid uuid;
begin
    cid := direct_chat_id(auth.jwt() ->> 'sub', other_id);

    insert into chats (id, is_group) values (cid, false)
    on conflict (id) do nothing;

    insert into chat_members (chat_id, user_id) values
        (cid, auth.jwt() ->> 'sub'),
        (cid, other_id)
    on conflict do nothing;

    return jsonb_build_object(
        'chat_id', cid,
        'messages', coalesce((
            select jsonb_agg(m order by m.created_at desc)
            from (
                select * from messages
                where chat_id = cid
                  and (before is null or created_at < before)
                order by created_at desc
                limit page
            ) m
        ), '[]'::jsonb)
    );
end;
$$;
```

Один RTT вместо трёх: **~200 мс вместо 520 мс**. А с локальным кэшем — 0 мс.

## Слой 3. Отправка через уже открытый WebSocket

Сейчас отправка — новый HTTP-запрос (137 мс), потом ещё realtime-хоп (~100 мс).

У нас уже есть постоянное WebSocket-соединение Supabase Realtime.
Идеальный путь:

```
1. Сразу нарисовать сообщение у себя (status: pending)      — 0 мс
2. Отправить Broadcast по существующему сокету              — ~30–50 мс до получателя
3. Параллельно INSERT в Postgres                            — 137 мс, durable
4. Получатель по ack заменяет pending на confirmed          — ~140 мс
5. Нет ack за 10 с → «не доставлено», можно повторить
```

Получатель видит сообщение через **50–80 мс**, а не через 240.
База остаётся источником истины: pending-сообщение либо подтверждается, либо помечается ошибкой.
Фантомов нет, потому что у сообщения есть явный статус.

Важно: сейчас перед отправкой код **ждёт** `refreshSupabaseToken()`, а это вызов Apps Script
(2.6–3.5 с). Если токен истекает во время переписки — сообщение зависает на 3 секунды.
Обновление токена нужно делать **заранее в фоне**, а в отправке никогда не ждать.

## Слой 4. Префетч

Пользователь не должен ждать даже 200 мс.

- Наведение курсора / `touchstart` на контакт → prefetch последних 50 сообщений.
- При старте приложения → prefetch 5 самых свежих чатов.
- При открытии приложения → prefetch списка контактов и статусов.

К моменту клика данные уже в памяти. Открытие = 0 мс всегда, а не только для старых чатов.

## Слой 5. Убрать Apps Script из горячего пути

Apps Script — 2.6–3.5 с на вызов. Всё, что через него идёт, обречено быть медленным.

| Сейчас через Apps Script | Заменить на | Время |
|---|---|---|
| Удаление сообщения «у всех» | RLS `UPDATE` из клиента | 3 с → **~150 мс** |
| Удаление чата | RPC `security definer` | 3 с → **~150 мс** |
| Отправка push | Database Webhook → Edge Function → FCM | 3 с → **~300–800 мс** |
| Загрузка файлов | Supabase Storage напрямую | 10 с → **1–2 с** |
| Импорт стикеров Telegram | Edge Function (токен в секретах) | 5–10 с → **1–3 с** |
| Вход / JWT | можно оставить: раз в 30 дней | 3 с, но редко |

Apps Script остаётся только для входа и миграции старых аккаунтов.
Из обычной работы он уходит полностью.

## Слой 6. Файлы напрямую в Storage

```
Сейчас:  браузер → base64 → Apps Script → Drive → ссылка
Стало:   браузер → signed upload URL → Supabase Storage (CDN)
```

- 1 ГБ бесплатно, отдача через CDN.
- Картинки сжимаются на клиенте (уже есть).
- В сообщении хранится путь, а не публичная ссылка Drive.
- Drive можно оставить как архив: после загрузки Edge Function копирует файл туда фоном.

Эффект: **5–15 с → 1–2 с**, и картинки начинают открываться мгновенно.

## Слой 7. Push через webhook

```
INSERT в messages
   └─ Database Webhook (Supabase)
        └─ Edge Function
             └─ FCM v1
```

Никакого Apps Script. Уведомление приходит через **0.3–0.8 с** после сообщения,
а не через 3+ секунды. Токены устройств можно хранить в таблице `push_tokens`.

---

## Слой 8. Обходной путь: P2P-сообщения (эксперимент)

Если оба онлайн, сообщение можно гнать по WebRTC DataChannel — тому же, что используется в звонках.

- Доставка **20–50 мс**, быстрее любого сервера.
- База пишется параллельно, для истории и офлайна.
- Если канал не установлен за 1–2 с — fallback на WebSocket.

Минусы: соединение поднимается 1–3 с, на мобильном в фоне канал умирает,
сложность и баги. Как основной путь — не стоит. Как «турбо-режим» для активной переписки — можно.

---

## Физика: регион базы

Один запрос сейчас — 130–215 мс. Это в основном расстояние до региона Supabase.
Если проект в США, перенос в Европу даст **−80–100 мс на каждый запрос**.
Это больше, чем все оптимизации кода вместе.

Проверить регион: Supabase Dashboard → Project Settings → General → Region.
Смена региона = новый проект + `pg_dump`/restore. Делать только после того,
как код перестанет делать лишние запросы.

## Порядок работ

**Этап 1 — «мгновенное открытие» (1 вечер, без SQL)**
1. Кэш `uid` и `chatId` в localStorage.
2. Пропуск профиля и RPC, если данные известны.
3. Рендер из локальной истории до ответа сети.
4. `preconnect` к Supabase, фоновая замена JWT без блокировки отправки.
5. Префетч по наведению/касанию.

**Этап 2 — «один запрос» (1 вечер, нужен SQL)**
1. RPC `open_chat`.
2. RLS-политика на удаление своего сообщения.
3. Применить `delete-features.sql`.

**Этап 3 — «убрать трёхсекундные пути» (2–3 вечера)**
1. Supabase Storage для файлов.
2. Database Webhook + Edge Function для push.
3. Перенос импорта стикеров в Edge Function.

**Этап 4 — «турбо» (по желанию)**
1. Отправка через WebSocket с ack.
2. Детерминированный `chat_id`.
3. Смена региона базы.
4. P2P DataChannel.

## Риски

- **Локальный кэш** нужно версионировать и чистить; иначе старые сообщения могут «залипнуть».
- **Несколько устройств** — кэш на каждом свой, конфликтов нет, но история догружается по `lastTs`.
- **WebSocket-отправка** требует честного статуса pending/confirmed, иначе вернутся фантомы.
- **Storage** — 1 ГБ бесплатно, дальше платно; Drive-архив решает.
- **Edge Functions** — холодный старт 100–300 мс, всё равно в 10 раз лучше Apps Script.
- **Смена региона** — миграция проекта, простой на время переноса.

---

## Что не надо делать

- Не переписывать всё на фреймворк ради скорости — DOM здесь не узкое место.
- Не кэшировать агрессивно HTTP-ответы Supabase — данные быстро устаревают.
- Не гнать сообщения только через Broadcast без записи в базу — это и были фантомы.
- Не тащить Redis/очереди на бесплатном тарифе — они не нужны при таком объёме.

## Что уже внедрено (v20)

Замеры на проде, ноябрь 2026.

| Что | Результат |
|---|---|
| Повторный запуск приложения | **0 вызовов Apps Script**, первый запрос к Supabase на 72 мс |
| Открытие знакомого чата | **2–3 мс** до экрана, 1 запрос ~70–90 мс |
| Отправка сообщения | вставка **86 мс**, доставка получателю **118 мс** |
| Список чатов на новом устройстве | появляется сразу (раньше ждал 30 с) |
| Синхронизация всех чатов | **1 запрос** вместо N (раз в 30 с) |
| Префетч | наведение на контакт греет чат до клика |
| Файлы | Storage-путь + автоматический откат на Drive |
| Удаление «у всех» | быстрый путь проверяет, что строка реально обновлена |
| Вход | ник подставляется сам, фокус сразу в пароле |

Как это сделано:

- JWT Supabase кэшируется в `localStorage` на 12 часов; при запуске проверяется
  срок и совпадение `sub`/`nick`, иначе — обычный обмен через Apps Script.
- `uid` и `chatId` хранятся в `pps.chats`; профиль и `create_direct_chat`
  запрашиваются только если их нет.
- Знакомый чат грузит только новое (`created_at > lastTs`), а не последние 200.
- Если локальной истории нет — грузится полная страница; если чат удалён —
  он пересоздаётся автоматически.
- Префетч по наведению (180 мс задержки, чтобы клик не дублировал запрос).
- Синхронизация всех чатов — один запрос `chat_id in (...)`.
- Файлы сначала пробуют Supabase Storage, при ошибке — Google Drive.
- Токен обновляется в фоне и никогда не блокирует отправку.

Осталось применить `messenger/supabase/speed.sql` — он включает:

- мягкое удаление «у всех» без Apps Script (~150 мс);
- удаление чата «у обоих» без Apps Script;
- бакет `media` для быстрых файлов;
- индекс `pg_trgm` для поиска по нику;
- Realtime для сообщений.

До применения SQL: удаление идёт через Apps Script (~3 с),
удаление чата «у обоих» недоступно, файлы идут на Drive.
