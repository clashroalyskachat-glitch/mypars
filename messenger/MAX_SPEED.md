# pps — максимум скорости: все варианты

Ноябрь 2026. Что уже работает, где физический потолок и какие технологии
реально могут дать следующий шаг.

---

## 1. Где мы сейчас

Замеры на проде после v21:

| Операция | Время |
|---|---|
| Повторный запуск приложения | 0 вызовов Apps Script, первый запрос к Supabase ~70–280 мс |
| Открытие знакомого чата | 2–3 мс до экрана, 1 запрос ~70–90 мс |
| Отправка (своё сообщение) | 4 мс |
| Доставка получателю (turbo) | **67–85 мс** |
| Загрузка списка чатов | сразу |
| Синхронизация всех чатов | 1 запрос раз в 30 с |

Сеть в тестовом окружении: Cloudflare colo **ARN** (Стокгольм),
RTT до Supabase **120–135 мс**. База, судя по DNS, в Европе
(`eu-north-1`, Стокгольм). Для пользователя в Сибири это те же
60–100 мс физического расстояния.

Главное: **85 мс — это уже почти один сетевой RTT**. Код дальше почти
ничего не даст. Дальше выигрывают только топология и инфраструктура.

## 2. Потолок текущей архитектуры

```
отправитель → Supabase Realtime (регион) → получатель
                 ↑
          один RTT до региона
```

Чтобы стать быстрее, нужно убрать регион из горячего пути:

```
отправитель → ближайший edge → получатель
                    ↓
             Supabase (асинхронно, для истории)
```

Или вообще убрать сервер:

```
отправитель ←──── WebRTC DataChannel ────→ получатель
                    (оба онлайн)
```

Всё остальное — микрооптимизации.

## 4. Google: что реально есть

Google не даёт «магически быструю» запись для браузерного чата.

- **Firebase Firestore** — локальный кэш и latency compensation: интерфейс
  мгновенный, но подтверждение с сервера всё равно ~100–200 мс.
  Плюс vendor lock-in и цена за чтения.
- **Firebase Realtime Database** — WebSocket + локальный кэш; та же история.
- **Cloud Run** — обычный контейнер в регионе; скорость как у Supabase,
  но появляется ops.
- **Spanner** — глобальная консистентность, запись 100 мс+; для чата избыточен.
- **Global External HTTPS Load Balancer** — anycast, может улучшить маршрут,
  но не уберёт RTT до региона.
- **WebTransport/QUIC** — с марта 2026 Baseline во всех браузерах
  (Safari 26.4). Убирает head-of-line blocking и ускоряет рукопожатие,
  но **не уменьшает RTT уже установленного соединения**. Для чата выигрыш
  около нуля; для видео/файлов полезнее.
- **FCM** — push, не транспорт сообщений.

Вывод: у Google лучший вариант — Firebase, но он не быстрее нашей
текущей схемы. Настоящий edge у Cloudflare.

## 5. Cloudflare: лучший бесплатный edge

Durable Objects с SQLite **доступны на Workers Free** (документация,
18.10.2026):

- 100 000 запросов/день;
- 13 000 GB-s/день;
- 5 ГБ SQLite;
- 5 млн чтений строк/день, 100 тыс. записей/день;
- WebSocket-сообщения считаются как 1/20 запроса;
- hibernation делает idle-соединения почти бесплатными.

Это значит: **edge-relay можно поднять бесплатно**.

### Схема relay

```
A ──wss──► Cloudflare edge (DO) ──wss──► B      ~20–50 мс
      └──► Supabase INSERT (история) ──┘        асинхронно
```

- Клиент отправляет сообщение в DO и параллельно пишет в Postgres.
- Получатель видит сообщение через ближайший edge, не дожидаясь региона.
- Если relay недоступен — приложение автоматически работает через Supabase.
- История и RLS остаются в Postgres.

Код уже лежит в `messenger/edge/` (Worker + Durable Object + JWT-проверка).
Нужно только задеплоить и вписать URL в `config.js`.

### DO + SQLite как edge-база

Можно пойти дальше: хранить последние сообщения в SQLite внутри DO,
а Postgres синхронизировать фоном. Тогда открытие чата и история тоже
будут с edge. Минусы: консистентность, миграции, второй источник истины.
Делать только если relay уже мало.

### D1 и Hyperdrive

- **D1** — SQLite на edge, но запись идёт в primary-регион; для чата не даёт
  чуда.
- **Hyperdrive** — пул соединений к Postgres; ускоряет установку соединений,
  не сам запрос.

## 6. VPS-релей: лучший вариант для России и Сибири

Если пользователи в Новосибирске, а база в Стокгольме, физика ~60–100 мс.
VPS в Москве/Новосибирске даёт 10–40 мс до клиента:

```
клиент → VPS (Москва/Новосибирск) → получатель   ~20–40 мс
                  ↓
           Supabase (фоном)
```

- Hetzner CX22 — €3.79/мес (Германия/Финляндия).
- Timeweb/Selectel/Aeza — от ~200–400 ₽/мес, Москва/Новосибирск.
- На VPS: Centrifugo (Go) + TURN (coturn) + write-behind в Supabase.
- Бонус: решает проблему бесплатного TURN для звонков.

Минус: появляется сервер, обновления, мониторинг. Но это самый большой
реальный выигрыш для сибирских пользователей.

## 7. P2P DataChannel

- 20–50 мс, $0, без сервера.
- Но соединение поднимается 1–3 с, на мобильном в фоне умирает,
  NAT/симметричные сети требуют TURN.
- Как основной путь — плохо. Как «турбо при обоих онлайн» — можно,
  но выигрыш над edge-relay небольшой, а сложности много.

## 7a. Экзотика: бинарный протокол, ИИ-маршрутизация, роевая память

### Бинарный протокол

Замер в `speed.html` на реальном браузере:

| | JSON | Binary | Разница |
|---|---|---|---|
| Размер сообщения | 173 Б | 111 Б | **−36%** |
| 10 000 encode+decode | 6 мс | 29 мс | **binary медленнее** |

Вывод: в браузере бинарный протокол **экономит байты, но не время**.
JSON-парсер нативно оптимизирован, а ручная сборка байтов в JS стоит
дороже. На RTT 100 мс 62 сэкономленных байта — доли миллисекунды.
Имеет смысл для файлов, видео и нативных клиентов (C++/Rust), не для текста.

### ИИ-маршрутизация

Настоящая маршрутизация в интернете — это **anycast и BGP**
(Cloudflare, Google Premium Network, AWS Global Accelerator), а не ИИ.
ИИ может предсказывать и прогревать соединения, но для сообщений
размером 100 байт это не даёт ничего.

Практичные приёмы, которые реально работают:

- **Hedged requests** — отправить запрос двумя путями и взять первый ответ.
  У нас уже есть «гонка»: relay и Supabase INSERT идут параллельно.
- **Latency-based routing** — выбрать ближайший edge по замерам.
- **Anycast** — Cloudflare сам направляет пакет в ближайший PoP.
- **Prefetch** — уже сделано.

### Роевая память (swarm memory)

CRDT (Automerge, Yjs), gossip (SWIM), edge KV, Redis/Dragonfly.
Это про **offline-first, presence, реакции и группы**, а не про RTT 1:1.
Для колледжа избыточно: Postgres — источник истины, а локальный кэш
уже даёт мгновенное открытие. Роевая память не сделает доставку быстрее
физического RTT.

## 8. Как выбрать

1. Открой `messenger/speed.html` на ПК и телефоне, в Wi-Fi и LTE.
2. Смотри RTT до Supabase:
   - **< 80 мс** — код уже на пределе; делай relay только если нужны <50 мс.
   - **80–150 мс** — ставь Cloudflare DO relay (бесплатно).
   - **> 150 мс** — нужен VPS ближе к пользователям или смена региона.
3. Если пользователи в Сибири и RTT > 100 мс — VPS в Москве/Новосибирске
   даст больше, чем любой edge.

## 10. Порядок следующих работ

1. **Замерить** реальные устройства через `speed.html`.
2. **Задеплоить edge relay** (бесплатно) и включить `PPS_RELAY_URL`.
3. **Применить `supabase/speed.sql`** — удаление, файлы, поиск.
4. **Push через DB Webhook → Edge Function** — убрать 3 секунды.
5. **TURN** (Cloudflare/LiveKit/свой coturn) — надёжность звонков.
6. **VPS в России** — если замеры показывают >100 мс.
7. **P2P / edge-база** — только если всего вышеперечисленного мало.

## 11. Транспортный deep dive: QUIC, BBRv3, XDP

### QUIC и HTTP/3

- Браузер уже может ходить в Supabase по HTTP/3: Supabase отдаёт
  `alt-svc: h3`, Chrome/Edge это используют. Но **Realtime — это WebSocket
  поверх TCP**, а не HTTP/3.
- WebTransport (QUIC в браузере) стал Baseline в марте 2026 (Safari 26.4).
  Но **Cloudflare Workers не умеет принимать WebTransport**: в workerd нет
  QUIC/HTTP3, tracking issue переведён в обсуждение в марте 2026.
  Supabase WebTransport тоже не даёт.
- Чтобы использовать WebTransport, нужен свой сервер с QUIC
  (quiche/quinn/Node rwebtransport) — то есть VPS.
- Что даёт: 0-RTT при переключении Wi-Fi → LTE, отсутствие HOL-блокировки
  между потоками, устойчивость к потерям. **Базовый RTT не уменьшает.**
- Вывод: для «всегда 100 мс» бесполезно; для «на мобильном иногда лагает»
  может помочь, но только с VPS.

### BBRv3

- BBRv3 есть в свежих ядрах Linux (2026), но CUBIC остаётся дефолтом;
  включать надо вручную: `net.ipv4.tcp_congestion_control=bbr`.
- Работает только на **вашем** сервере. На Supabase и Cloudflare вы
  алгоритм контроля перегрузок не меняете.
- Помогает большим передачам на потерянных каналах (файлы, видео).
  Для сообщений в 100 байт разницы нет.
- Вывод: включить на VPS, если он появится; на текущий стек не влияет.

### Anycast и edge termination

- TLS-хендшейк уже терминируется на ближайшем PoP Cloudflare (ARN).
  Поэтому «anycast» у нас уже есть.
- 120 мс — это не хендшейк, а путь **edge → регион Supabase**.
- Убирает его только вычисление на edge (Durable Object) или релей
  ближе к пользователю. AWS Global Accelerator / Cloudflare Argo
  оптимизируют магистраль, но стоят денег.

### WebRTC Data Channels

- Хороши для «печатает…», «доставлено» и текста **во время звонка**,
  когда DataChannel уже поднят.
- Как основной транспорт плохи: установка 1–3 с, NAT, фон на мобильном.
- Вывод: побочный канал для звонков, не замена relay.

### Protobuf / FlatBuffers / Cap'n Proto

- Замер: JSON 173 Б → binary 111 Б (−36%), но в JS binary encode+decode
  **медленнее** (29 мс против 6 мс на 10 000 сообщений).
- FlatBuffers zero-copy хорош в C++/Rust; в браузере всё равно копирование
  из сетевого буфера и граница WASM.
- Вывод: для текста не нужно. Для файлов и нативных клиентов — да.

### DPDK / XDP

- Имеет смысл при миллионах пакетов в секунду и 10–100 Гбит/с.
- У нас десятки пользователей; XDP может пригодиться только для DDoS-фильтра
  на своём VPS.
- Вывод: не делать.

## 11a. Спекулятивный handshake, CRDT и Argo

### Pre-warming (сделано)

- `relayPrewarm()` прогревает DNS + TLS до edge при старте.
- `IntersectionObserver` прогревает чаты, которые появляются на экране.
- Наведение на контакт прогревает чат за 180 мс до клика.
- При открытии чата сразу поднимаются `user-<uid>` и relay-сокет.
- При возврате во вкладку сокеты переподключаются.

### TLS 1.3 и session resumption

Cloudflare уже отдаёт TLS 1.3 и session tickets; повторное подключение
идет за 1-RTT. 0-RTT early data в браузере предназначен для идемпотентных
HTTP-запросов; для WebSocket-апгрейда на него рассчитывать не стоит.
Ничего дополнительно включать не нужно.

### CRDT (Yjs / Automerge)

Для 1:1 текста CRDT избыточен. Порядок и дедупликация уже решены:
`created_at` от сервера + `client_id` + сортировка при слиянии.
CRDT нужен для offline-редактирования, реакций, групповых чатов
и совместных документов — там, где два клиента меняют одно состояние.
Для сообщений он добавит вес и сложность без выигрыша в задержке.

### Cloudflare Argo

Argo оптимизирует путь edge → origin. У нас edge ARN и регион Supabase
тоже Европа (Стокгольм), поэтому оптимизировать почти нечего.
Argo даёт 10–30% на длинных маршрутах (например, edge в Европе → origin
в США). Если регион базы когда-нибудь переедет за океан — тогда имеет смысл.
Стоит денег, включается в панели Cloudflare.
